Executive Summary

Use this section to understand what already exists, what is still missing, and what "prototype complete" means for the current iPhone plan.

Implemented Today

Current App Scope

  • App bootstrap
  • Pairing UI
  • QR scanning
  • Manual pairing-link fallback
  • Pairing scan, status polling, and completion
  • Refresh token persistence in Keychain
  • Stable installationId persistence in Keychain
  • Local paired-device context persistence
  • Post-pairing placeholder screen
Not Implemented Today

Missing Major Areas

  • Launch-time session restore
  • General authenticated API layer
  • Inventory list and detail
  • Item create and item edit flows
  • Planning update UI
  • Movement, rental, and return UI
  • Item history UI
  • Admin item archive UI
  • Admin location-management UI
  • Automated tests
Definition Of Complete Prototype

Done Means

  • QR pairing activates the iPhone as a device
  • Stable installation identity is stored in Keychain
  • Refresh token is stored in Keychain
  • Access token stays in memory only
  • Recoverable paired-device summary may stay in UserDefaults
  • The finished authenticated shell uses a tab bar root
  • Future launches refresh and open directly into inventory unless revoked
  • Inventory, editing, planning, movement, and history match the shared backend contract
  • EDITOR and ADMIN role boundaries are respected

Implemented Backend Contract

This is the backend surface the current iPhone app already calls today. It is pairing-only.

POST
/api/mobile/pairings/scan
  • Request: pairingToken, installationId, suggestedName, platformName, platformVersion, modelName
  • Returns: MobilePairingStatusResponse
  • Does: submits the scanned QR pairing token and device metadata
GET
/api/mobile/pairings/{id}
  • Request body: none
  • Returns: MobilePairingStatusResponse
  • Does: polls the pairing session until completed, cancelled, or expired
POST
/api/mobile/pairings/{id}/complete
  • Request body: none
  • Returns: MobilePairingCompleteResponse
  • Does: exchanges a completed pairing for device session material and tokens
Error
Standard Error Envelope
  • Shape: { error: { code, message, details } }
  • Current client support: decodes code and message; ignores details

Build Order

Recommended implementation sequence for the next iOS developer.

  1. Finish session bootstrap. Expand AppModel, add DeviceSessionModel, add auth DTOs, and implement refresh/logout/me support.
  2. Finish inventory browsing. Add inventory models, list UI, detail UI, and authenticated entry routing into the inventory branch.
  3. Finish item create and item edit. Add BusinessDate, editor state models, author lookup, location lookup, and duplicate-number handling.
  4. Finish planning updates. Add promised-organization search/create and expected-leave-date editing.
  5. Finish admin item and location actions. Add archive item support and admin-only location management.
  6. Finish movement and history. Add movement request UI and history UI once the final backend response DTOs are confirmed.
  7. Finish tests and QA. Add targeted unit tests and verify the full LAN flow on a real iPhone.
